## 2026-10-22: dialogue-recovery (ветка feature/dialogue-recovery)

Реализованы runtime-переходы до новой записи: предстоящий визит той же специальности → явный выбор оставить / перенести / отменить / создать ещё один. Проверка повторяется сервером под lock перед резервом; согласие относится к конкретному звонку и снимку будущих визитов. Неопределённая транзакция не повторяется новым operation_key или другим слотом. Ошибки формы отделены от записанной runtime-ошибки МИС. Дневной сбой произносит установленную фразу и передаёт человеку; ночью предлагает согласованный callback 10:00–16:00 с учётом календаря регистратора, при отказе — отдельную заявку без перезвона, без визита и без СМС до подтверждённой записи. Контекст и транскрипт передаются в заявку и recovery.

Проверки: 59 Python tests (recovery/CRM/hours), 24 Rust lib tests (включая четыре новые развилки FSM), cargo fmt/clippy проходят. Подробности и команды: debug/runs/dialogue-recovery/. Тесты используют временную SQLite и локальный контрактный mock; внешнюю МИС/реальную LLM не вызывают.

НЕ закрыто: реальный production API reasoning-провайдер не настроен (есть opt-in callable, режим production, запрет CI/Actions/act, фиксированная схема уточнения, 2s ожидания, один активный анализ и запрет записи/повтора). Полного автономного исправления запроса после уточнения нет: ответ попадает в сохранённую историю, затем callback/заявка.
